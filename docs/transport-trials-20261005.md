# New transport trial findings — 2026-10-05

Scope: two additive nodes with USA/Germany egress; retain existing working USA Reality TCP and Germany WS. This is protocol research, not evidence of current reachability from Iran. Source-of-truth for AtlasAndroid compatibility is Xray **v26.7.28**, rather than older design discussions.

## Candidate priority

1. **XHTTP + TLS + Cloudflare ECH, HTTP/2** for both countries, if an owned proxied hostname and origin configuration are available. It adds a different access path and hides the hostname in ClientHello. ECH hides the actual SNI behind Cloudflare's public name; it does not hide the destination edge address or guarantee availability. Cloudflare says ECH is enabled by default on Free zones. [Cloudflare ECH](https://developers.cloudflare.com/ssl/edge-certificates/ech/)
2. **XHTTP + REALITY, direct HTTP/2, stream-one** if CDN/ECH prerequisites or client import support fail. This removes the CDN dependency and streams both directions in one request, but still needs a reachable origin address and does not add ECH. REALITY is a separate transport security choice; use it instead of TLS in this candidate. [REALITY documentation](https://github.com/XTLS/Xray-docs-next/blob/main/docs/en/config/transports/reality.md)
3. **RAW/TCP + REALITY + Vision** remains the performance/compatibility baseline. It duplicates the working USA method, so does not satisfy the requested transport diversification by itself. “REALITY + TLS + Vision” is misleading: security is REALITY or TLS; Vision is VLESS flow. Xray rejects Vision over ordinary XHTTP unless separately using VLESS Encryption; use empty flow for these XHTTP trials. [Exact v26.7.28 VLESS implementation](https://github.com/XTLS/Xray-core/blob/v26.7.28/proxy/vless/outbound/outbound.go)

These priorities are engineering judgments, not speed predictions. Use separate USA/Germany origins and verify outbound egress geography; CDN edge geography is not VPN egress geography.

## Exact settings and compatibility traps

- **Set modes explicitly.** v26.7.28 auto selects **packet-up for TLS**, including H2; REALITY auto selects stream-one, or stream-up with downloadSettings. Earlier XHTTP discussion text saying TLS H2 auto uses stream-up is stale for this version. The same source selects H3 only for exactly `alpn: ["h3"]`; adding h2 does not give automatic H3 fallback. REALITY uses H2. Start with `alpn: ["h2"]`. H3 requires working UDP and merits a later independent trial. [Exact version dialer](https://github.com/XTLS/Xray-core/blob/v26.7.28/transport/internet/splithttp/dialer.go)
- **CDN mode trials:** packet-up is the compatibility baseline; explicit stream-up may improve sustained upload. For Cloudflare's gRPC handling, origin must expose TLS/H2 with h2 ALPN on 443, hostname must be proxied, SSL mode at least Full, and gRPC enabled. Keep the default application/grpc header. Public Cloudflare Tunnel hostnames do not support gRPC. [Cloudflare requirements](https://developers.cloudflare.com/network/grpc-connections/), [XHTTP author's design discussion](https://github.com/XTLS/Xray-core/discussions/4113)
- **Keep streaming alive:** v26.7.28 defaults scStreamUpServerSecs to 20–80 seconds and sends padded response keepalives when the expected padding/legacy marker is present. Preserve defaults initially; packet-up server POST limit must be at least the client's limit. [Versioned defaults](https://github.com/XTLS/Xray-core/blob/v26.7.28/transport/internet/splithttp/config.go), [Versioned server](https://github.com/XTLS/Xray-core/blob/v26.7.28/transport/internet/splithttp/hub.go)
- **ECH is a client setting, not just a dashboard switch.** tlsSettings.echConfigList accepts a fixed base64 config or resolver URL such as an HTTPS DoH endpoint. Dynamic lookup requests HTTPS/type65 records for serverName; a reachable resolver is a bootstrapping dependency. Missing/stripped ECH config fails connection rather than intentionally falling back to plaintext SNI. Prefer encrypted DNS and verify both ECH retrieval and handshake. DoH uses DialSystem, relevant to Android VPN socket protection/routing. Static configs can become stale after key changes. [Exact v26.7.28 ECH implementation](https://github.com/XTLS/Xray-core/blob/v26.7.28/transport/internet/tls/ech.go), [TLS configuration](https://github.com/XTLS/Xray-docs-next/blob/main/docs/en/config/transports/tls.md)
- **ML-DSA is optional and separate from ECH.** v26.7.28 implements mldsa65Verify; omit seed/verify initially for unknown client builds. When enabled, matching server/client keys are required. Official docs require the target certificate to exceed 3500 bytes to avoid a size fingerprint; fully post-quantum negotiation additionally requires target X25519MLKEM768 support. [REALITY documentation](https://github.com/XTLS/Xray-docs-next/blob/main/docs/en/config/transports/reality.md), [Versioned verification](https://github.com/XTLS/Xray-core/blob/v26.7.28/transport/internet/reality/reality.go)

## Acceptance before publishing

AtlasAndroid's known core has the needed primitives; that does not prove its URI parser preserves mode, extra, ALPN or echConfigList. v2rayNG/V2Box/Happ versions are unknown: inspect generated JSON after import, then test each actual app. A successful latency probe alone is insufficient. Compare bounded sustained download/upload, reconnect/drop behavior, idle recovery, and real web/app use from the intended Iranian connection. Promote exactly one proven USA and one proven Germany candidate; label anything tested only outside Iran as server-side validated, Iran unverified.

## Radar screenshot follow-up — 2026-10-05
- Radar's traffic-volume chart measures change against a previous period, using traffic observed by Cloudflare; it is not a packet-loss or VPN-success measurement. A point at -53% means the selected observed metric is about 53% below its comparison baseline, not that 53% of the Internet is blocked. Confirm the sign, metric, year, timezone, and comparison window before quoting a number. [Chart methodology](https://blog.cloudflare.com/http-requests-on-cloudflare-radar/), [Iran traffic](https://radar.cloudflare.com/traffic/ir)

National aggregation cannot identify MCI/TCI/Irancell behavior, fragmentation effectiveness, or blocked Hetzner/OVH ranges. [Radar data scope](https://developers.cloudflare.com/radar/)
- Primary-page retrieval exposed chart labels but no dated Oct 3–5 point values/outage records; filtered dated views failed to load. No current Cloudflare primary report corroborating the claimed last-two-days event was found. This is unavailable verification, not evidence that disruption did not occur. [Iran traffic](https://radar.cloudflare.com/traffic/ir), [Outage Center](https://radar.cloudflare.com/outage-center)
- Even very low HTTP/3 share measures successful observed request composition, not proof that all UDP is blocked; aggregate volume also cannot distinguish a Cloudflare incident from Iranian filtering or routing changes. Use dated operator-level observations and actual client tests. [HTTP dataset scope](https://developers.cloudflare.com/radar/investigate/http-requests/)
